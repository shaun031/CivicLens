# Phase12 offline evaluation and measurements

Run `python -m app.scripts.evaluate_intelligence` using the backend virtual environment.
Fixed labeled synthetic scenarios are generated by code, not operational records. All methods run
against the same labels; no test chooses a winning method in advance. Results below were actually
measured2026-10-20 and are NOT real-world generalization, calibrated probabilities or legal findings.

## A. Recurrence candidate suggestions

48 pairs:12 scenarios ×4 small coordinate perturbations. Scenarios include verified repeats,
unverified/failed repairs, simultaneously unresolved reports, different potholes20m apart, explicit
distinct-object wording, absent/different-angle photos, far locations, category mismatch, horizon,
equal repair timestamp and later verified recurrence. Positive means a synthetic repeated physical
issue; prediction means a candidate suggestion, NOT administrator confirmation.

| Method | TP | FP | FN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|
| Location only |16|28|0|0.3636|1.0000|0.5333|
| Location + text |16|28|0|0.3636|1.0000|0.5333|
| Location + text + optional image |12|24|4|0.3333|0.7500|0.4615|
| Verified-history full evidence |16|4|0|0.8000|1.0000|0.8889|

Image matching worsens recall for changed viewpoints in this fixture. Full logic still suggests
nearby distinct potholes. It must NOT automatically confirm or merge them. English templates are
narrow; four perturbations are not independent real-world samples. Thresholds need field validation,
held-out geographic/category data and explicit asset evidence before operational accuracy claims.

## B. Repair verification simulated policies

40 claims from eight fixed reference/feedback/reviewer scenarios repeated five times.15 disputed
claims;20 reference repairs need rework. Reviewer outcomes are explicitly noisy synthetic inputs.

| Simulated policy | Incorrect closures | Incorrect nonclosures | Agreement |
|---|---:|---:|---:|
| Officer claim only |20|0|0.50|
| Citizen majority |10|10|0.50|
| Administrator review |5|5|0.75|

These are comparisons of SIMULATED policies, not field performance or proof that a human reviewer
is always correct. The real application does not implement citizen-majority closure. All official
decisions require accountable administrator review; absence of feedback is not confirmation.

## C. Geographic sensitivity

12 constructed comparisons:3/10/30 incidents per underlying area ×0.01/0.1-degree grids ×same versus
different severity/department mix. Underlying areas have24h versus96h work starts and different SLA
outcomes, with equal canonical incident counts.0.01 grid:3 observations yields two insufficient-data
cells and no flag;10/30 yields one potential service-review flag.0.1 grid collapses the areas into
one cell and correctly reports insufficient OTHER-area comparison. Priority/department differences
remain visible rather than causally controlled. Raw equal incident volume cannot identify the
constructed delay difference; reporting counts are not used as a service-need denominator.

This sensitivity experiment demonstrates grid/sample effects, not a discrimination detector. No
population, road-length or infrastructure inventory reference data is fabricated. Unoccupied areas
and missing timestamps are not treated as successful service observations.

## Reproducible performance protocol

Run `python -m app.scripts.benchmark_intelligence`. It creates a TemporaryDirectory database with
1000 reports,500 canonical incidents,6 departments and6 officers, then performs20 real repair/request
creation, citizen response and ADMIN approval transactions. Analytics uses the full bounded cohort.
The script reports sample counts and actual timings; cold versus revision-cached queries are separate.

One measured local run (not an AWS forecast): repair+request creation14.081ms median/20 samples;
response11.875ms/20; approval12.744ms/20; historical candidate retrieval/scoring18.026ms/3 (one actual
temporally eligible historical candidate/check, using one later real singleton probe); cold
fairness27.917ms/1; cached fairness1.675ms/5; CSV1.768ms/1,2289 bytes. Mixed existing
P10 event batch of100 measured18476.530ms/1, including queued synthetic complaint triage—not per-event
repair latency. Timings depend on machine load/caches; these are observations, not acceptance SLAs.
Image upload/transfer latency and actual cloud IAM/capacity are not benchmarked. Existing P6 image
matching evaluation separately measures comparison limitations. No developer database is seeded/reset.
